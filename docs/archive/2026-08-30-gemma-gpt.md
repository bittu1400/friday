# Gemma 4 + MTP: Local Voice-Agent Fit and Hardware Plan

**Date:** 2026-08-30  
**Scope:** check-only. No application code, service configuration, model files, or system settings were changed.  
**Machine:** Core Ultra 9 275HX (8P + 16E cores), RTX 5070 Laptop GPU with 8,151 MiB VRAM, 16 GiB RAM.

## Decision in one page

Gemma 4 12B QAT is a credible *quality* upgrade for Friday: it matched the current model on the existing planner evaluation, is noticeably better at conversational replies and some alias extraction, and has the multimodal and multilingual headroom that a local voice agent can grow into. It is not currently a drop-in performance upgrade: the measured base configuration leaves just **214 MiB VRAM** free and is substantially slower than the present Qwen 2.5 7B.

Unsloth does provide an MTP drafter for the exact Gemma artifact. MTP is the right kind of acceleration because target-model verification preserves the normal model output distribution; it does **not** reduce model quality. But it is not free on this laptop: the smallest MTP GGUF alone is about 242 MiB before its runtime allocations, so it cannot be added to a deployment with 214 MiB free. Unsloth also advises planning material extra RAM/VRAM headroom. Therefore: **do not enable MTP until measured headroom has been created and quality gates pass.**

The recommended posture is to retain Gemma as the candidate, keep the present Qwen deployment until the missing planner tests are fixed, and treat MTP as a second-stage benchmark—not an assumed 1.5–2x improvement. The best no-quality-loss optimizations are already largely in place: full GPU offload, 8-bit KV cache, server-resident weights, prompt-prefix reuse, a dedicated LLM GPU process, and disabling unused multimodal projection weights. MTP is the next quality-preserving speed lever, once it fits.

## MTP: what is true, and what is not

MTP is speculative decoding with draft heads trained alongside the target model. The heads propose several future tokens; the full model verifies them before they are committed. With the usual exact speculative-decoding acceptance procedure, output is identical under greedy decoding and sampled from the same target distribution under stochastic decoding. In other words, **MTP improves throughput, not intelligence, and does not trade away output quality.** [llama.cpp’s speculative-decoding documentation](https://github.com/ggml-org/llama.cpp/blob/master/docs/speculative.md) describes this verifier-and-acceptance design; Google lists a dedicated speculative-decoding draft model as a Gemma 4 feature in its [Gemma 4 overview](https://ai.google.dev/gemma/docs/core?authuser=0).

### Availability

Unsloth's repository for the evaluated model contains companion MTP GGUFs:

| File | Size | Implication |
|---|---:|---|
| `mtp-gemma-4-12B-it-Q4_0.gguf` | 253,708,800 bytes (~242 MiB) | Smallest sensible first candidate |
| `mtp-gemma-4-12B-it-Q8_0.gguf` | 465,127,936 bytes (~444 MiB) | Higher-precision drafter |
| BF16 / F16 MTP | 861,538,816 bytes (~822 MiB) | Not appropriate for this 8 GiB card |

The installed `llama.cpp` build already advertises `draft-mtp`; no rebuild is inherently required. The eventual compatible shape is a base GGUF plus MTP GGUF with `--spec-type draft-mtp`; exact flags must be checked against the installed build's help and Unsloth's model card when implementation is authorized.

### The hard constraint

MTP **does increase live memory use** here. The base model has 214 MiB free; even the Q4 drafter is ~242 MiB before its KV cache, verification graph, and CUDA workspace. It will fail or force undesirable memory pressure. Treat any claim that MTP provides a 1.5–2x speedup "without increasing VRAM" as inapplicable to this configuration.

MTP is likely most valuable for Friday's free-text chat turns (about 62–77 output tokens), where decode accounts for 86–89% of measured turn time. It is less certain for the grammar-locked planner: it emits about 22 tokens and grammar constraints may lower draft acceptance. Bench acceptance and wall time separately for planner and chat; do not generalize a vendor throughput figure to this workload.

## Gemma 4 qualities for a local voice agent

### Strengths observed in Friday

- **Planner correctness:** 28/28 on the current evaluation, with no regressions versus Qwen in those fixtures.
- **Closed-set behavior:** it remained within Friday's constrained action schema on the evaluated suite.
- **Better conversation:** the recorded human review found more useful, concrete, naturally conversational replies—important because a spoken assistant's quality is not captured by JSON fixtures.
- **Better utterance normalization:** it correctly reduced examples such as “open my todo” to the usable `todo` alias and removed filler from some music requests.
- **Efficient 12B option:** the QAT GGUF fits where a conventional 12B Q4_K_M artifact tested at ~7,305 MiB of weights does not.
- **Native future headroom:** Google positions Gemma 4 as multimodal (text/image, with audio in selected sizes), multilingual, long-context, and MTP-capable. It can generate text only, which remains appropriate for Friday’s separate STT/TTS pipeline today. [Google’s model overview](https://ai.google.dev/gemma/docs/core?authuser=0), [Gemma 4 technical report](https://arxiv.org/abs/2607.02770).

### Caveats that matter more than marketing

- **It is not faster on this laptop without MTP.** Its token rate and planner/chat latency are lower than Qwen’s.
- **Tight VRAM is a reliability risk.** A display, CUDA workspace fluctuation, or a second GPU workload can turn a stable-looking load into OOM or fallback behavior.
- **Reasoning must be disabled correctly.** The measured Gemma setup spent roughly 63 of 85 output tokens on thinking when enabled. Use the server/model’s supported `--reasoning off` path when implementation is authorized; do not use a formatting switch that exposes thought text to user history or TTS.
- **The test suite is incomplete.** Gemma returned `action=none` for a valid clipboard command despite 28/28. The same gap also hid a close-window failure in another candidate. No model swap should be approved until those missing behavior tests exist.
- **Do not load the vision projector.** It was not loaded in the measurements, so Gemma’s multimodal capability costs no GPU memory today. Loading it would be a scope and resource expansion, not an optimization.

## Hardware-load plan, ordered by quality safety

“No quality compromise” is strict. The table distinguishes mechanisms that preserve the selected model’s behavior from changes that can be safe only after validation.

| Priority | Practice | Hardware effect | Quality status / action |
|---:|---|---|---|
| 1 | Keep model loaded in one long-lived `llama-server` | Eliminates reload and cold-start work each turn | No model-quality cost; already the deployment model. |
| 2 | Preserve full GPU offload and verify it after every restart | Keeps latency off the CPU and preserves CPU for audio/UI | No quality cost; fail closed if CUDA is unavailable rather than silently CPU-serving. |
| 3 | Reuse the system-prompt prefix (`cache_prompt`) | Avoids recomputing 1,222 constant prompt tokens per turn | No quality cost; measured cache reuse already works. |
| 4 | Retain Q8_0 K/V cache | Halves KV memory versus FP16 while retaining the existing tested configuration | Present, measured configuration; do not lower KV precision without rerunning planner and human voice tests. |
| 5 | Keep `mmproj` unloaded | Avoids multimodal weights and GPU work not used by the text LLM path | No quality cost for current text-in/text-out architecture. |
| 6 | Explicitly verify/enable Flash Attention if supported | Reduces attention workspace/bandwidth pressure | Numerically equivalent attention algorithm in normal supported use; verify with the actual build rather than assume `auto`. |
| 7 | Set one request slot only if measurement shows slots consume separate KV | May release unused KV allocation; Friday has one turn in flight | No conversational-quality cost, but measure first: current server reports unified KV and automatic four slots, so savings are unknown. |
| 8 | MTP after sufficient headroom is demonstrated | Accelerates decode while target verifies tokens | Output-quality preserving; requires a controlled benchmark and room for drafter runtime. |

### Conditional compromises—not approved as “free” optimizations

- **8,192 → 4,096 context:** likely the largest way to make MTP fit, but it changes the long-turn capacity. It may be acceptable only if realistic max prompts stay below 4,096 tokens and the server is configured to fail rather than silently discard the system contract. Measure actual KV allocation first.
- **Q8_0 → Q4_0 KV cache:** frees more VRAM but adds accumulated state quantization error. It may prove imperceptible for Friday’s short working context, but it is not a no-quality-loss claim until both grammar tests and human listening tests pass.
- **Smaller weight quantization:** rejected for this goal. The selected QAT artifact is already the practical quality/fit point; lowering it to make MTP fit is a model-quality trade and should not be assumed acceptable.
- **Reduced GPU power/clock limit:** can reduce heat and fan noise, but necessarily lowers decode speed. It is a thermal/battery choice, not a performance optimization.
- **Smaller physical batch:** can reduce scratch memory but slows prompt processing. It attacks a small part of a cached voice turn and is a last resort.

## Recommended path before an implementation phase

1. Restore/verify NVIDIA driver health, then confirm actual GPU offload; do not treat an HTTP health endpoint as proof of CUDA use.
2. Close the planner-evaluation gap with fixtures for clipboard and window actions. This is the acceptance gate for a Gemma swap.
3. Make the product choice on measured trade-off: stronger chat and aliases versus 891 ms planner p50 and 214 MiB VRAM headroom.
4. If Gemma is chosen, first run an observation-only server load with verbose logs to establish flash-attention state, sliding-window/KV allocation, and whether four slots materially cost VRAM.
5. If genuine headroom remains insufficient, obtain explicit approval before reducing context to 4,096 with a fail-closed context policy. Do not change weight or KV precision first.
6. Only then add the Q4 MTP drafter and benchmark `--spec-draft-n-max` across a small sweep. Record: VRAM peak, output equality/fixture result, accepted-token rate, planner p50, chat p50, thermal/power behavior, and regression-free voice listening results.
7. Keep MTP only if it remains stable under concurrent audio work, improves the free-text path materially, and retains the quality gates.

## Bottom line

Gemma 4 12B QAT has the right qualitative profile for Friday, especially for the part users hear: conversation, instruction discipline, and future multimodal capability. It is feasible as a base model but tight. MTP is legitimate, quality-preserving acceleration, not a quality-reducing compression trick—but it does **not** fit on top of the currently measured 8 GiB Gemma configuration. The optimized, quality-first answer is: preserve the current tested QAT + Q8 KV setup, keep the model resident and prompt-cached, leave multimodal weights unloaded, prove exact runtime allocations, and only make the smallest reversible context/slot trade that produces enough measured headroom for an MTP benchmark.
