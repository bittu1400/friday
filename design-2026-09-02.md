## 1. The one idea everything hangs off

A capability lives in **ten** places today. Every recent defect is a place
someone forgot. The fix is fewer places.

Audit F12 counted **nine**. **Phase 1 added the tenth**, and that is worth
stating plainly because it is the argument for Phase 3 in miniature: F1's fix
was specified here as *"one gate, called at every side-effecting entry"*, and
what shipped was **eight `config.is_disabled()` checks in `turn.py` plus four
more across `clipboard.py`, `typer.py` and `notifier.py`**. It works — it was
probed live with `FRIDAY_DISABLED=1` and all ten paths fail closed — but a new
side-effecting capability now needs its own panic gate, hand-written, in the
right place. **Phase 3 must derive the gate from `risk`, not just the confirm
policy.** See criterion 3.5.

**One record. Everything else derived.**

```python
class Risk(Enum):
    NONE       = "none"        # read-only. never confirms.
    LOW        = "low"         # reversible, undramatic. never confirms.
    FIRST_USE  = "first_use"   # confirms once per subject, then remembered
    ALWAYS     = "always"      # confirms every time
    NAMED      = "named"       # confirms every time AND speaks the consequence

@dataclass(frozen=True)
class Capability:
    id:        str
    params:    Mapping[str, ParamSpec]      # enum | text | ref
    summary:   str                          # ONE line -> planner prompt
    persona:   str                          # ONE clause -> chat prompt
    examples:  tuple[Example, ...]          # >=2. eval fixtures. NOT optional.
    risk:      Risk
    subject:   Callable | None              # what FIRST_USE remembers
    hotwords:  tuple[str, ...]              # STT bias
    describe:  Callable | None              # habits-miner phrasing  (F21)
    audit:     Callable[[Params], dict]     # what may be recorded (FR-26/57)
    handler:   Handler                      # Subprocess | Store | Inline | Recipe
    plannable: bool = True                  # may appear in a multi-action plan
    terminal:  bool = False                 # may only be the sole action  (§6.5)
```

Derived mechanically, each with a test asserting the derivation:

| derived | replaces | kills |
|---|---|---|
| `PARAM_SCHEMA` | hand-written dict | schema drift |
| `plan.gbnf` / `final.gbnf` | committed files | grammar drift |
| `SYSTEM_POLICY` action block | 25 hand-written lines | F3 |
| `CHAT_SYSTEM` toolset clause | hand-written prose | **F2, structurally** |
| the confirm decision | 5 hand-coded branches | F12 |
| a required eval fixture | `eval.jsonl` by hand | F3 |
| `STT_HOTWORDS` | hand-written string | the "wifi → wife" class |
| `habits.describe_action` | a 4-branch if-chain | **F21** |
| the audit row shape | per-call-site dicts | audit blind spots |

The persona can no longer contradict the schema **because it is the same
string**. That is F2 closed by construction.

### 1.1 What the refactor may never touch

1. The model emits an **id from a closed set** and **typed params**. Never a
   path, URL, shell string, or argv element.
2. **Code builds argv.** Grammar *and* application validation. Fail closed.
3. **Execute first, then speak** from an outcome template.

### 1.2 Prompt growth

`SYSTEM_POLICY` is **1298 tokens** (measured). One line per capability. Fine to
about **40**. Past that, group into families (`system.*`, `window.*`, `file.*`,
`media.*`, `memory.*`, `time.*`, `app.*`, `recipe.*`) and let the planner choose
a family then a member. Because `summary` is a field, that is a **rendering
change**, not a rewrite. Design for it now; build it when the token count says
so.

## 3. Confirm, at scale

### 3.1 Behaviour per tier

```
NONE / LOW   run. speak the outcome. audit row.

FIRST_USE    subject approved?  -> run, as LOW.
             not approved       -> "Open Discord? I'll remember."
                                   yes -> record approval, THEN run
                                   no  -> record the decline, store nothing

ALWAYS       "Are you sure you want to <description>?"   every time.

NAMED        "<consequence>. Are you sure?"              every time.
             The line NAMES what changes: which file, which destination,
             which recipe. Never a bare "are you sure".
```

`NAMED` exists because "Are you sure?" is not informed consent when the question
is *which* file moves *where*.

### 3.2 The panic switch is part of the gate

Per audit F1, the switch currently guards only the executor. In the new shape it
is checked **inside the gate**, before any handler runs, for **every** tier —
including the FIRST_USE approval write, the store handlers, and the recipe
handler. One place, all capabilities.

### 3.3 The first-use allowlist (D-3)

Migration `004_approvals.sql`:

```sql
CREATE TABLE IF NOT EXISTS approvals (
  kind        TEXT NOT NULL,     -- 'app' | 'recipe' | 'device'
  subject     TEXT NOT NULL,     -- closed-enum id, never free text
  argv_sha256 TEXT NOT NULL,     -- fingerprint of what was approved
  approved_at INTEGER NOT NULL,
  PRIMARY KEY (kind, subject)
);
```

**`argv_sha256` is not optional, and v1 omitted it.** App ids are derived from
the `.desktop` `Name` (`desktop.app_key(name)`), and `scan()` resolves a key
collision with `setdefault` — first wins. So two different applications can
normalise to one id, and an uninstall followed by an install can silently hand a
stored approval to a **different binary**. The fingerprint closes that: if the
argv behind an approved id has changed, the approval **does not apply** and
Friday asks again, naming the change.

Rules, each a test:

- An approval is written **only** from a completed confirm handshake. No code
  path lets the planner create one.
- The subject is a closed-enum id, never a phrase, never a path.
- Approvals are **never** swept by retention (user intent, like preferences).
- Revocation is keyboard-only: `just approvals list | forget <id> | reset --yes`.
  **Not built yet** — `just approvals` and `just recipes` are Phase 3/4d
  deliverables. `just --list` is authoritative for what exists today.
  Voice grants; only the keyboard revokes.
- The panic switch blocks the **approval write**, not merely the launch.

**Tier assignment** lives in `desktop.py`, derived from `Categories` plus a
code-owned override table for T3. Code, never a model judgement.

Measured on this machine — 103 distinct apps:

- **T1 → FIRST_USE (85)** — browsers, terminals, editors, IDEs, chat, media,
  office, viewers, file managers, monitors, utilities.
- **T2 → ALWAYS (13)** — `firewall_configuration`,
  `advanced_network_configuration`, `bluetooth_manager`, `bluetooth_adapters`,
  `nvidia_x_server_settings`, `print_settings`, `manage_printing`,
  `qt5_settings`, `qt6_settings`, `kvantum_manager`, `thunar_preferences`,
  `fcitx_5_configuration`, `appimagelauncher_settings`.
- **T3 → NAMED (5)** — `timeshift`, `oracle_virtualbox`, `debian_box`,
  `forgetales_on_debian_box`, `android_file_transfer_mtp`.

The current code gates all 28 `Settings`-category entries, including
`about_xfce`, `uuctl` and `fcitx_5_migration_wizard`. That noise goes.

### 3.4 Dynamic enums (Bluetooth, audio sinks, windows)

Targets discovered at runtime cannot be baked into the grammar. Same pattern as
§5, and it is the **only** pattern used for this:

1. A `NONE` capability enumerates them and assigns **ordinals**, held in a
   pending slot with the confirm window's lifetime.
2. The acting capability takes an **ordinal from a closed set** (`1..5`); code
   maps it back to the MAC / sink id.

The model never sees or supplies a device address.

## 4. The command library — option (b)

### 4.1 Contract

- **The owner authors. Friday never writes, edits, or varies a recipe.**
- **No arguments** (D-6). `argv` is fixed at author time. The model supplies only
  a recipe **id**.
- `~/.config/friday/recipes/*.toml`, dir `0700`, files `0600`, enforced on read
  the way `store/db.py` enforces the database.
- Loaded into a **closed enum**. The grammar never enumerates param values, so a
  large library costs zero prompt tokens; only `name` and `description` reach
  the prompt.

```toml
id          = "deploy_blog"
name        = "deploy the blog"
description = "builds and publishes the blog"
argv        = ["/home/bittusah/bin/deploy-blog.sh"]
risk        = "named"
consequence = "This will build and publish your blog live."
unsafe      = false
```

### 4.2 Validation at load (v1 omitted this)

An `id` becomes a **grammar enum member**, so it is validated before it can
reach the grammar:

- `id` must match `^[a-z][a-z0-9_]{0,31}$`. Anything else: refused, logged,
  named at startup. A malformed id could otherwise corrupt `plan.gbnf`.
- `id` must not collide with an existing capability or app id.
- `argv` must be a non-empty list of strings. No string form. No shell.
- `argv[0]` must resolve via `shutil.which` **or** exist as a file, at load time.
- `risk` must be one of the enum; absent means `named`.
- `consequence` is required when `risk` is `named`.

### 4.3 Reload semantics (v1 omitted this)

Recipes are read **once at startup**, because the enum feeds the grammar and the
grammar must not change mid-turn. Editing a recipe requires
`systemctl --user restart friday`. `just recipes reload` is explicitly **not**
provided: a live enum swap during an in-flight turn is the kind of race this
project has already paid for twice.

### 4.4 Shell stays in a file the owner wrote

`argv` is an argv list, `shell=False` (invariant #3, unchanged). A recipe needing
a pipeline points at a **script the owner wrote**:

```toml
argv = ["/home/bittusah/bin/backup-projects.sh"]
```

The shell lives in a file a human authored, read and saved. Friday assembles
nothing. That is the whole difference between (b) and (c).

### 4.5 `unsafe = true`

The ban list blocks `rm`, `pacman`, `systemctl`, `sudo`. A library that cannot
touch any of those is not useful — but a silent bypass makes (b) into (c). So
the bypass is explicit, per recipe, and expensive:

- Set by the owner, by hand, in the file.
- **Forced to `Risk.NAMED`** regardless of the file's `risk`. Every run confirms
  and speaks `consequence`.
- The file must be `0600` and owned by the user, or it is refused at load with a
  spoken reason. A recipe another process can write is a recipe another process
  can run.
- `just recipes list` marks it; `just selftest` **prints the unsafe count** as
  its own line, so it is never invisible.
- **Still forbidden with `unsafe`:** anything irreversible. `unsafe` widens the
  binary denylist; it does not repeal invariant #10. Concretely, the executor
  still refuses a recipe whose resolved argv (after wrapper resolution, audit
  F5) names a filesystem-destroying or partition-level binary — `mkfs*`, `dd`,
  `fdisk`, `parted`, `shred`, `wipefs`. Package management, service control and
  `rm` become reachable; disk destruction does not.

### 4.6 What (b) may never become

Written down so a later session cannot drift there by increments:

- No recipe arguments from the model, of any kind.
- No Friday-authored recipes.
- No recipe that selects or composes another recipe.
- No `shell=True`, ever, anywhere.
- No recipe in a **multi-action plan** — `run_recipe` is `terminal` (§6.5).

Any one of those is option (c): explicit written go-ahead plus an invariant
amendment.

## 5. Filesystem — resolve, then choose

### 5.1 The pattern

```
  user   "open the invoice I saved yesterday"
    |
    v
  file_find{query:"invoice"}     query is TEXT and never becomes a path,
    |                            an argv element, or a glob
    v
  code searches the ROOT SET     -> at most 5 candidates
    |                               each gets an ordinal, held in a
    v                               PENDING SELECTION (RAM, 30 s window)
  "I found three. Invoice March,
   Invoice April, invoice-draft."
    |
    v
  user   "the second one"
    |
    v
  file_open{ref:"2"}             ordinal from a closed set;
    |                            code maps it to the real path
    v
  the path exists only in code
```

**Correction from v1:** the flow spans **two turns**, so refs are
**pending-scoped**, not turn-scoped — they live in the same slot, with the same
30-second window and the same barge-in clearing rules as a `PendingAction`. A
turn-scoped ref would be dead before the user could answer.

Properties, each testable:

- The model never sees a path. It sees titles and ordinals.
- A ref cannot be replayed, guessed, or carried into a later turn.
- Zero candidates is a **spoken outcome**, never a guess. That is exactly
  today's `file_open` defect (F15: substring match, first key wins).
- The pending selection is cleared by barge-in and by the 30-second timer, like
  every other pending.

### 5.2 The root set

Code-owned, one constant:

```
  ~/Documents  ~/Downloads  ~/Pictures  ~/Videos  ~/Music  ~/Desktop  ~/Projects
```

Excluded unconditionally, and the search cannot be talked out of it: any dotfile
or dot-directory, `~/.ssh`, `~/.gnupg`, `~/.local/state/friday`, anything inside
`.git/`, anything mode `0600` or stricter, and any symlink whose target leaves
the root set.

Search is an index (SQLite FTS over name + mtime), rebuilt on a debounce. Not a
live `find`: a `find` across 510 GB on the event loop is deafness.

### 5.3 Writes

`file_move`, `file_rename`, `file_trash` are all `NAMED`. The confirm names
source and destination:

> *"Move Invoice-April.pdf from Downloads to Documents. Are you sure?"*

Gate today (D-2): **PTT press + spoken confirm.** The key press is the presence
proof. The voiceprint hook is wired in this phase and **records a similarity
score into the audit row from day one**; it does not block. §9.

**Hard delete is permanently banned** (invariant #10). `file_trash` moves to
`~/.local/share/Trash` — reversible — and the spoken line says "moved to trash",
never "deleted".

## 6. Multi-action turns (D-4)

### 6.1 Grammar — MEASURED as feasible

```
root ::= "{" ws "\"actions\"" ws ":" ws "[" ws action
              ( ws "," ws action ){0,2} ws "]" ws "}" ws
```

Verified against the live server today. `{0,2}` bounded repetition is supported
by this llama.cpp build; an explicit-alternation form behaves identically.

```
 "open my browser and turn the volume up"          -> 2 actions, 1511 ms
 "open my browser, play some lo-fi, and turn
  the volume down"                                 -> 3 actions, 1662 ms
```

`final.gbnf` **does not change**. A turn that consumed untrusted data still
emits exactly one action, named `none`.

### 6.2 The validator must change (v1 said otherwise)

`validate()` rejects any top-level key but `action` — that check is what stops
AS-4. A multi-action plan therefore needs an explicit change, not a reuse:

- Accept **exactly one** top-level key, `actions`, a list of 1–3 objects.
- Validate **each element** through the existing per-action path unchanged.
- **Any** element failing fails the **whole plan** closed to `none`. A
  partially-valid plan is not a plan.
- The single-action form is **removed**, not kept alongside. Two accepted
  shapes is the C1 defect (two implementations of one protocol) waiting to
  happen.

### 6.3 Execution

```
  panic switch checked BEFORE EACH STEP, not once per turn
  for each step, in order:
      gated?  -> confirm now, at the step, not up front
                 yes -> run, audit, continue
                 no  -> "Stop here, or carry on with the rest?"      (A-1)
                        stop  -> abort remaining, audit them 'aborted'
                        carry -> skip this step, continue
      run
      failure -> STOP. Do not continue past a failed step.
                 Speak what succeeded and what did not.
```

- **One turn in flight** (FR-5) covers the **whole plan**.
- Each step writes its **own audit row**, sharing a `plan_id`. A half-run plan
  must be fully readable afterwards.
- The spoken outcome is assembled from per-step outcome **templates**, never the
  LLM (invariant #4).
- **No step may be irreversible** (invariant #10, unchanged).

**A mid-plan confirm needs a plan cursor** — v1 missed this. The daemon's
`_pending` is a single slot holding one `PendingAction`. Resolving a confirm in
the middle of a plan must restore the remaining steps, so the pending becomes
`(action, remaining_steps, plan_id)`. Its 30-second expiry aborts the **whole
plan**, not just the step, and says so.

### 6.4 The latency fast path (new in v2)

The multi-action grammar costs **+109 ms on every turn** (816 → 925 ms p50),
which the 1-action case must not pay:

```
  utterance contains a coordinating token ("and", "then", ",", "also")
      -> multi-action grammar
  otherwise
      -> single-action grammar   (the fast path, 816 ms)
```

A heuristic, and it fails **safely**: a missed conjunction costs the second
action, the user says it again. It never causes an extra action.

### 6.5 Two rules that keep invariant #1 intact (new in v2)

1. **Steps pass no data to each other.** Not now, not later. Each step's params
   come from the plan the model emitted **before** any step ran. If a later
   change ever lets step 2 read step 1's output, an untrusted result could steer
   a dispatch — the exact attack T1 exists to prevent. Enforce it with a test on
   the sequencer's signature.
2. **Terminal capabilities may not appear in a plan at all.** `web_search`,
   `screen_look`, `file_find` and `run_recipe` are `terminal = True`. The first
   two consume untrusted data; the third needs a user turn in the middle; the
   fourth is (b)'s escape hatch and stays a deliberate, single, confirmed act. A
   plan containing a terminal capability fails closed to `none`.

### 6.6 At most one gated step per plan

A three-step plan with two confirms is worse than three separate commands. If
the planner produces a plan with two or more gated steps, run the **ungated
prefix**, then say *"the rest needs confirming — say it again on its own."*
Under-deliver rather than interrogate.

## 7. Screen vision — an opt-in skill (D-7)

### 7.1 Invocation

Never automatic. Reachable only from the user's own words ("look at my screen",
"what's this error"). Not by anaphora, not by history resolution (ADR-065
already blocks that), and not as a plan step (`terminal = True`).

### 7.2 Risk is ALWAYS, not NONE (corrected from v1)

`clipboard_read` is gated because reading it aloud can voice a password. **A
screenshot leaks strictly more than a clipboard.** A misheard trigger would
photograph your screen and describe it out loud. So `screen_look` is
`Risk.ALWAYS`: nothing is captured until an explicit yes. Being opt-in is not a
substitute for a gate — a mishear is exactly what a gate is for.

### 7.3 A screenshot is untrusted data

Text on screen can be attacker-authored — a web page, a chat message, an email.
So a vision turn is exactly a web-search turn:

- locked to **`final.gbnf`**
- **cannot dispatch**, structurally, whatever the screen says
- output sanitized before speech, as in `grounding.py`
- never written to disk (invariant #7): `grim` to stdout, held in RAM, dropped
  at end of turn

The single most important decision in this section. Do not build vision without
it.

### 7.4 Placement (A-2)

Per invocation: GPU if free VRAM ≥ model footprint + margin, else CPU. Measured
today: **1131 MiB VRAM free** (llama-server holds 7010 of 8151), **~4 GiB system
RAM free**. Honest expectation: **CPU almost always**, so a CPU-viable model
must be chosen first.

Model selection is its own **ADR-041 drill** — enumerate candidates,
`uv pip install --dry-run` before installing, benchmark on this laptop in
`balanced`, pin by SHA256, record the rejected alternatives. Hard constraint:
`onnxruntime-gpu` in this venv would break invariant #6, so a GPU path needs a
separate process or an amendment.

## 8. Latency — the budget, rebuilt (D-5 reopened)

### 8.1 Measured across all three power profiles (audit §E.1)

Run at the owner's request, 2026-09-02. Machine returned to `power-saver`.

| stage | power-saver | **balanced** | performance |
|---|---|---|---|
| STT p50, 20 real clips | 1059 ms | **653 ms** | 643 ms |
| STT p95 | 1142 ms | **699 ms** | 724 ms |
| planner p50, single-action grammar | 818 ms | **691 ms** | 656 ms |
| TTS synth, 10 chars | 375 ms | **224 ms** | 213 ms |
| TTS synth, 117 chars | 2452 ms | **1401 ms** | 1337 ms |
| Kokoro RTF, long line | 0.263 | **0.150** | 0.143 |

**`balanced` is the target and `performance` is not worth taking.** Performance
improves STT p50 by 10 ms (1.5%) and makes **p95 worse** (724 vs 699) — inside
noise, for thermal and battery cost.

Two corrections this forced:

- v2 of this file budgeted STT at **~800 ms** in balanced, quoting the project's
  record. Measured: **653 ms p50, 699 p95**. I was pessimistic by ~150 ms.
- v2 implied the planner was GPU-bound and profile-independent. It is **not**:
  818 → 691 ms, a **127 ms** CPU-side term.

### 8.2 The wall, re-confirmed (audit F26)

STT cost is **flat in audio length in every profile**. In `balanced`:

```
  1.0s audio -> 556 ms      3.0s audio -> 641 ms
  2.0s audio -> 594 ms      5.0s audio -> 688 ms
```

Five times the audio for 1.24× the cost. Whisper pads to a 30-second window;
`faster_whisper 1.2.1` exposes no streaming API. **Chunked or streaming STT
gains nothing here, at any clock speed.** The wall is architectural.

### 8.3 A third latency term nobody had named (audit F29)

**MEASURED:** `executor._LAUNCH_GRACE_S = 0.4`, and a GUI app never exits, so the
`wait_for` always runs the full grace:

```
  detach=True  (GUI launch): 402 ms
  detach=False (command)   :   2 ms
```

So **launches and commands do not have the same budget**, and every previous
version of this table conflated them.

### 8.4 The real budget, balanced, after the planned changes

Streaming TTS in place; single-action fast path (§6.4); ~50 ms daemon overhead
(asyncio hops, the threaded `prompt_digests` read).

| stage | command action | **launch action** | chat |
|---|---|---|---|
| STT p50 | 653 | 653 | 653 |
| planner p50 | 691 | 691 | 691 |
| execute | 2 | **402** | — |
| chat generation (200-char cap in code) | — | — | ~900 |
| TTS **first chunk**, streamed | 224 | ~250 | ~224 |
| daemon overhead | ~50 | ~50 | ~50 |
| **TTFA** | **~1.62 s** | **~2.05 s** | **~2.52 s** |

Against the 1.5 s / 2.5 s target:

- **command actions — 1.62 s.** 120 ms over. Borderline.
- **launch actions — 2.05 s.** Over, and **402 ms of it is the grace** (§8.6).
- **chat — 2.52 s.** Effectively on target.

The changes that produce it, by value:

1. **Streaming TTS** — removes reply length from TTFA. *(−1177 ms on chat.)*
2. **Move to `balanced`** — *(−406 ms STT, −127 ms planner: −533 ms on every
   turn.)* Free. No code.
3. **Conditional second planner call** — *(−691 ms on `none` turns.)*
4. **Single-action fast path** (§6.4) — *(−109 ms on ordinary turns.)*
5. **Enforce the 200-char cap in code** (audit F6). Its value after streaming
   TTS is bounding generation and speaking time, not TTFA — a first chunk costs
   ~224 ms whatever follows. Do it as a **control** (a prompt is not one), and
   claim no TTFA win for it.

### 8.5 D-5R — the decision, with real numbers

| | option | command | launch | chat | cost |
|---|---|---|---|---|---|
| **a** | balanced + streaming TTS, keep the grace | 1.62 s | 2.05 s | 2.52 s | nothing |
| **a+** | as (a) **plus §8.6**, grace 400→150 ms | 1.62 s | **1.80 s** | 2.52 s | a narrower launch-failure signal |
| **b** | (a+) **plus STT on CUDA** | **1.07 s** | **1.25 s** | **1.97 s** | **amends invariant #6.** Contends for VRAM (1131 MiB free). Project measured p95 **107 ms**, 7.5×. |
| **c** | (a+) plus a variable-length STT model | ~1.4 s | ~1.6 s | ~2.3 s | project measured ~4× faster **and 10/20 misses vs 4/20**. Accuracy loss. |

**Recommendation: (a+).** It clears 1.5 s on commands within noise, brings
launches to 1.8 s, hits chat, and costs no invariant. Reserve **(b)** for a
Phase 5 evaluation with its own ADR — invariant #6 exists because STT stealing
VRAM from the LLM under load is a real failure, and that has not stopped being
true.

Reject **(c)**: 10/20 misses is not a latency trade, it is a different product.

### 8.6 The launch grace — a decision (audit F29)

`_LAUNCH_GRACE_S = 0.4` costs **402 ms on every GUI launch**. It exists to catch
a binary that dies at startup.

| | option | saves | costs |
|---|---|---|---|
| keep 400 ms | — | 0 | the status quo |
| **shorten to 150 ms** | **252 ms** | catches a binary that dies inside 150 ms instead of 400. `which()` already preflighted; a real exec failure still raises `FileNotFoundError` → NOT_FOUND. **Recommended.** |
| drop the wait | 402 ms | the outcome template already says *"Launching X."* and never claims a window — but the last cheap signal that the spawn survived is gone. |

Recommend **150 ms**, measured: it is the lazy correct answer, and a binary that
dies between 150 and 400 ms is already reported OK today.

### 8.7 Making a target real

A target nothing can fail is a wish.

- `selftest` **FAILs** when the power profile is not `balanced` — and per audit
  **F28** it must read `powerprofilesctl get` or
  `/sys/firmware/acpi/platform_profile`. The obvious implementations (the
  governor, `scaling_max_freq`) read **identically in all three profiles** and
  produce a check that can never fail. Write the FAIL-path test.
- `just stats` reports p50/p95 TTFA **by action class** — commands, launches and
  chat have different budgets (§8.4) and one number hides that.
- The budget table lives in the repo. A regression against it is treated like an
  eval regression: reverted, or justified in writing.

## 9. Voiceprint — hook now, gate later (D-2)

### 9.1 What was measured

Best case: voiceprint built from **all 20** real mic clips, then those same
clips scored against it — training data as test data. Threshold **0.75**.

```
full clips (2.0-7.0s), same speaker, own training data:
  0.506  0.562  0.576  0.602  0.631  0.654  0.662  0.773  0.784  0.801
  0.808  0.825  0.831  0.877  0.889  0.891  0.896  0.898  0.912  0.936
  -> 7 of 20 BELOW threshold.

short slices, i.e. what a spoken "yes" is:
  0.4s: 0.224-0.365      0.6s: 0.208-0.344
  1.0s: 0.216-0.465      1.5s: 0.356-0.603
  -> every one below 0.75. 100% false reject.
```

*(v1 reported "6 of 20" and printed only 19 values — `0.898` was lost in
sorting. Corrected here.)*

The model does **not** crash on short audio: 10–30 ms on 0.3–2.5 s, CPU. The
SIGSEGV in this project's record is an NPU-only artefact. The problem is that
half a second of one word does not carry enough voice, and 0.75 was never
calibrated against data.

There is also a **content mismatch**: enrollment reads ten long scripted
sentences (`speaker_enroll.ENROLLMENT_PHRASES`), while verification would score
a short natural reply. Enrollment and verification are not measuring the same
thing.

### 9.2 What ships now

- Gate = **PTT + spoken confirm** naming the consequence.
- `SpeakerVerifier` runs on **every gated confirm anyway** and writes its
  similarity score into the audit row. It **never blocks**.
- After a few weeks that column **is** the calibration dataset: real voice, real
  mic, real confirm phrases.

### 9.3 The six conditions before the gate turns on

1. A voiceprint is enrolled (`just enroll-voice`; **none exists today**).
2. Threshold chosen from ≥200 logged real confirms, not a constant.
3. Measured **false-reject rate below 2%** on the owner, from that data.
4. At least one **impostor sample** exists, proving the threshold rejects
   something. A threshold that has never rejected anyone is not a control.
5. Verification runs on the **command utterance** (2–7 s), not the 0.5 s "yes".
6. The failure mode is decided in writing: fail **closed** once enrolled. Today
   it fails **open**, which is worse than absent — it invites the assumption
   that it works.

Until all six hold, the score is logged and ignored. The gate is being built on
evidence, not dropped.

## 10. Bootstrap (D-8)

`just bootstrap` — idempotent, and it **verifies rather than assumes**:

```
  1  python 3.12 venv via uv, `uv sync`         -> assert interpreter version
  2  fetch-voice   (Kokoro)                     -> SHA256 verified
  3  fetch-vad     (Silero)                     -> SHA256 verified
  4  fetch-wake    (hey_jarvis)                 -> SHA256 verified
  5  fetch-speaker (CAM++)                      -> SHA256 verified
  6  fetch-model   (Gemma 4 12B QAT)            -> SHA256 verified
  7  llama.cpp: detect the sm_120 build, or print the exact build command
     and STOP                                   -> assert, never continue blind
  8  DOCKER: assert dockerd is running and the user can reach it; pull the
     digest-pinned SearXNG image                -> audit F24; v1 omitted this
  9  SearXNG settings + unit link
 10  systemd: link + enable the three user units
 11  `just selftest`                            -> must be all-PASS, not
                                                   merely no-FAIL (audit F20)
```

Two rules, both learned from this codebase:

- **`just bootstrap --check`** runs every postcondition without doing anything,
  and **must be able to FAIL**. A bootstrap that reports success on a machine
  missing a model is the `gpu_arch` defect again.
- Every model download is **SHA256-pinned**, and no dependency may reach the
  network at runtime (audit F8).

Step 8 is not optional: Friday's search capability depends on **the Docker
daemon, running as root**, and the SearXNG unit itself documents that a `--user`
unit cannot express that dependency. A fresh machine without Docker gets a
degraded Friday and no explanation.

## 12. Definition of done

```
[ ] the acceptance test passes AND its FAIL path was demonstrated
[ ] `just eval` did not regress            (paste the line)
[ ] `pytest -q` green                      (paste the count)
[ ] committed grammars unchanged, or the change IS the point and is stated
[ ] ONE live spoken run, verified by the system's own readback
    (wl-paste, hyprctl clients, nmcli, sqlite) - never Friday's own words
[ ] a decision with alternatives has an ADR naming the rejected ones
[ ] evidence pasted, not summarised
[ ] a change touching a HARD INVARIANT ships with a mutation of that line
    demonstrated to turn the suite RED   (adopted repo-wide 2026-09-03, ADR-117)
```

Three rules this codebase has already paid for:

- **A green suite is not a working feature.** During Phase 3, run the live path
  after every step, not only the suite.
- **A check that cannot fail is worthless.** Every new test here carries a
  "prove the FAIL path" clause. F20 is that lesson landing on the self-test
  itself.
- **Measure before you promise.** v1 of this document committed to a latency
  target derived from an assumption about STT that a five-minute measurement
  disproved. Measure, then write the number down.
