## C. Verdict

The discipline here is real: fail-closed validation, execute-before-speak, a
closed action enum, an audit table, an error taxonomy, and comments that carry
the measurement behind each decision. Keep it. Do not rewrite it.

But it is a **25-action assistant with a hand-written dispatch chain**, and four
things stand between it and "everything on this laptop":

1. **Truth defects.** The panic switch misses ten side-effecting paths. Chat
   denies capabilities that work. The prompt tells the model to refuse 157 of
   the 162 apps it can launch. **`just selftest` prints "All required system
   checks passed" with no microphone, no LLM, and the panic switch engaged.**
   In text mode, quiet mode and dictation announce success and do nothing.
   All measured.
2. **The dispatch chain caps out.** 25 actions through 19 hand-written
   `if plan.name ==` branches, confirm policy hard-coded inside them, and a
   **1298-token** prompt that grows per action. Collapses around 40.
3. **Nothing is instrumented in production.** TTFA is logged only under
   `FRIDAY_DEBUG`, which is unset under systemd and suppressed there anyway.
   No watchdog. No metric.
4. **A physical latency wall nobody has measured.** STT cost is **flat in audio
   length** — ~900 ms fixed, whatever you say (F26). Every "make STT faster by
   streaming it" plan, including the one in v1 of my own design, is dead on this
   backend.

Order: **stop lying → make it measurable → make it extensible → make it wide →
make it fast.** Widening before step 3 multiplies the maintenance surface of a
shape that already does not scale.

cpu cur MHz under load              2700            5160            5200

  mean ms                           1031             642             646

  1.0s audio                         984             556             537

Kokoro TTS synth ms / RTF
  10 chars                   375 / 0.429     224 / 0.256     213 / 0.244

  p50                                818             691             656
  min                                795             656             625
  max                                873            1007            1002

Four things this settles:

1. **`power-saver` costs 1.6× on STT** (1059 → 653 p50) and **1.75× on TTS**
   (2452 → 1401 on the long line). Confirmed on this machine, not inherited
   from a document.
2. **`performance` buys nothing.** STT p50 improves 10 ms (1.5%) over
   `balanced`, and its **p95 is worse** (724 vs 699). TTS improves 4%. Inside
   run-to-run noise. `balanced` is the right target; `performance` is thermal
   and battery cost for no latency.
3. **`balanced` STT p95 is 699 ms**, which clears the 800 ms limit this project
   records as failing at 713–804. Under `balanced`, on this corpus, it passes.
4. **The planner is NOT purely GPU-bound.** p50 moves 818 → 691 ms across
   profiles — a **127 ms** CPU-side term (tokenization, HTTP, sampling, grammar
   evaluation). I had assumed it was profile-independent; it is not.

Chat generation was also measured but is **not comparable** across profiles:
temperature is 0.7, so each run produced a different reply of a different length
(54–130 chars). No conclusion is drawn from it.

**F26 holds in every profile.** In `balanced`, 1.0 s of audio costs 556 ms and
5.0 s costs 688 ms — still 1.24×, still dominated by fixed cost.

### F1 — S1 — The panic switch does not stop 10 side-effecting paths

**MEASURED.** With `FRIDAY_DISABLED=1` set:

```
  executor system_volume       -> disabled          (correct)
  friday.tools.clipboard       consults is_disabled: False
  friday.tools.typer           consults is_disabled: False
  friday.proactive.notifier    consults is_disabled: False
  friday.store.notes           consults is_disabled: False
  friday.store.reminders       consults is_disabled: False
  friday.turn                  consults is_disabled: False
  friday.daemon                consults is_disabled: False
```

`friday/tools/executor.py:63` is the only place `config.is_disabled()` is
consulted outside `selftest`. These ten run anyway:

| # | path | code |
|---|---|---|
| 1 | reach the network | `turn.py:_do_web_search` → SearXNG |
| 2 | write the clipboard | `turn.py:539` → `clipboard.set_clipboard` |
| 3 | read the clipboard **aloud** | `turn.py:556` → `read_clipboard` |
| 4 | type into the focused window | `daemon.py:346` → `typer.type_text` (ydotool) |
| 5 | write a preference | `turn.py:confirm_preference` |
| 6 | forget a preference | `turn.py:_do_forget` |
| 7 | create a timer | `turn.py:_do_set_reminder` |
| 8 | cancel a timer | `turn.py:_do_cancel_reminder` |
| 9 | create a note | `turn.py:_do_create_note` |
| 10 | desktop notification | `notifier.py:27` |

**Why it matters:** the panic switch is the control a user reaches for when
Friday is misbehaving. Friday will say *"I'm switched off."* to an `open_app`
and, in the same breath, type into your editor, overwrite your clipboard, read
it aloud, and query the network. A kill switch that kills some things is worse
than none, because it is trusted.

**Fix:** one gate, called at every side-effecting entry — not just the
executor's. Put it where the audit row is written; every side effect already
owes one, so the two obligations share a chokepoint.

### F20 — S1 — `just selftest` reports PASSED with no mic, no LLM, and the panic switch on

**NEW in v2. READ, and confirmed against `run_selftest`.**

`selftest.py:run_selftest` sets `has_fail` **only** on `Status.FAIL`. `WARN`
prints yellow and is then counted as success:

```python
if res.status is Status.WARN:
    prefix = ...          # printed, and that is all
else:
    has_fail = True       # FAIL only
...
print("[PASSED] All required system checks passed successfully.")
```

Every one of these returns **WARN**, so the run still ends `[PASSED]`:

| check | WARN condition | what is actually true |
|---|---|---|
| `panic_switch` | switch **ENGAGED** | Friday is deliberately disabled |
| `audio_devices` | no default input device | **Friday cannot hear** |
| `audio_devices` | `sounddevice` not installed | no voice in or out |
| `llm_on_gpu` | llama-server **not running** | there is no brain |
| `gpu_arch` | compute cap unparseable | architecture unverified |
| `gpu_arch` | `nvidia-smi` absent | ditto |
| `socket_binds` | no `ss`, no `/proc/net/tcp` | **invariant #8 unverified** |

**Why it matters:** "`just selftest` 8/8" is the sentence this project uses to
mean "the system is healthy". 8/8 is a count of checks that **ran**, not of
checks that **passed**. Right now every one genuinely passes — I ran it — so
this is latent, not active. But it is the same defect class as `gpu_arch`
passing through a GPU outage, in the tool built to catch that.

**Fix:** three states, three exits. FAIL → 1. WARN → a distinct exit code and a
distinct headline (`[DEGRADED]`), never `[PASSED]`. And `panic_switch` engaged
is not a warning about health — it is a **fact about intent** and belongs on its
own line, outside the pass/fail tally.

### F26 — S1 — STT cost is flat in audio length. Streaming STT cannot work here.

**NEW in v2. MEASURED.** Same clip, truncated:

```
  0.5s audio ->      2 ms   (internal VAD rejected it as silence)
  1.0s audio ->    991 ms
  2.0s audio ->    888 ms
  3.0s audio ->   1084 ms
  5.0s audio ->   1147 ms
```

Whisper is a **30-second-window** model: every input is padded to 30 s before
the encoder runs. Cost is ~900 ms of fixed work plus ~50 ms per second of real
audio.

**Re-measured in `balanced` and `performance` (§E.1): the shape is identical.**
In `balanced`, 1.0 s of audio costs **556 ms** and 5.0 s costs **688 ms** —
1.24×, for five times the audio. The wall is the model architecture, not the
clock speed.

**What this kills:** every plan of the form "transcribe incrementally during
capture so the tail is cheap". Transcribing a 1-second tail costs **991 ms** —
essentially the same as the whole utterance. `faster_whisper 1.2.1` exposes no
streaming API (`transcribe()` takes a complete array; there is a
`BatchedInferencePipeline`, which is throughput, not latency).

**This invalidates a target I had already committed to.** v1 of the design
budgeted STT at 250 ms via streaming and derived a 1.5 s direct-action target
from it. That budget was wrong. The honest floor on the current backend is:

```
  STT ~800 ms (balanced) + planner 816 ms + exec 50 + TTS first chunk 350
  = ~2.0 s, not 1.5 s
```

**The three real options**, and this is a decision, not an implementation:

| | change | measured effect | cost |
|---|---|---|---|
| a | **accept ~2.0 s** | — | nothing |
| b | **STT on CUDA** | the project measured **p95 107 ms**, 7.5× | **amends invariant #6** (only llama-server touches CUDA). Contends with the LLM for VRAM. |
| c | **a variable-length STT model** (e.g. Moonshine) | project measured ~4× faster | project also measured **10/20 misses vs 4/20**. Accuracy loss. |

Option (b) is the only measured path to 1.5 s. It is the owner's call and it
needs an invariant amendment first.

### F27 — S1 — In text mode, quiet mode and dictation speak success and do nothing

**NEW in v2. MEASURED by inspection.** `grep -n "dnd|dictation|scheduler"
friday/ui/tui.py` returns **nothing**. The TUI constructs no `DndManager` and no
`DictationManager`.

`turn.py:297` and `turn.py:355` return only the spoken line:

```python
if plan.name == "set_dnd":
    return TurnResult("set_dnd", {}, "Quiet mode enabled. ...", False)
```

The **daemon** applies the state change afterwards (`daemon.py:388-401`). The
TUI never does. So in text mode:

- "be quiet for a while" → *"Quiet mode enabled."* → nothing is enabled.
- "start dictation"      → *"Dictation mode enabled."* → nothing is enabled,
  and the next line is planned normally rather than typed.

**Why it matters:** this is ADR-009 inverted — speech without the action — and
it is the C1 shape again: two UIs, one of them wired. C1 was the TUI's confirm
handler; this is the TUI's state handlers. The same class of defect, in the same
file, found by the same question ("does the other UI do this too?").

**Fix:** the state change belongs in `turn.py` next to the outcome, or both UIs
take the managers. It must not be a caller's responsibility that only one caller
discharges.

**Related, and benign by luck:** the TUI also starts no scheduler, so a timer
set in text mode would never fire — except that the daemon runs as a service
against the same database and its scheduler picks the row up. That works by
accident, not by design.

### F28 — S2 — The power profile is invisible to every signal a check would naturally use

**NEW. MEASURED (§E.1).** In all three profiles:

```
  /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor  ->  "powersave"
  /sys/devices/system/cpu/cpu0/cpufreq/scaling_max_freq  ->  5400 MHz
```

Identical. The only signals that distinguish them are `powerprofilesctl get`,
`/sys/firmware/acpi/platform_profile`, and **`scaling_cur_freq` sampled under
load** (2700 vs 5160 MHz).

**Why this is a finding and not a footnote:** the fix I specified for the
profile problem is "a self-test check that FAILs in the wrong profile". The
obvious implementations — read the governor, read `scaling_max_freq` — **can
never fail**. That is precisely the `gpu_arch` defect: a check that asks a
question whose answer is always the same.

Any profile check must call `powerprofilesctl get` or read
`/sys/firmware/acpi/platform_profile`, and must have a test that proves the FAIL
path.

### F29 — S2 — Every GUI launch pays a flat 402 ms before Friday speaks

**NEW. MEASURED.** `executor._LAUNCH_GRACE_S = 0.4`. A detached launch is a GUI
app, so it never exits, so the `wait_for` **always** runs the full grace:

```
  detach=True  (GUI launch): 402 ms  outcome=ok  reported duration_ms=402
  detach=False (command)   :   2 ms  outcome=ok  reported duration_ms=1
```

So `open_app`, `open_youtube`, `youtube_search` and `file_open` each carry
**402 ms of dead time** between the spawn and the spoken line — a fifth of a
whole latency budget, on the most common thing a user asks for.

The grace exists to catch a binary that dies at startup. But the outcome
template already declines to claim a window appeared (`"Launching Brave."`, not
`"Opened Brave."` — ADR-043), `shutil.which` has already preflighted the binary,
and a binary that dies at 500 ms is reported as OK today anyway. The grace buys
a narrow signal at a fixed, universal cost.

**This is a decision, not a bug.** Options in `design-2026-09-02.md` §8.6.

### F5 — S2 — Wrapper prefixes walk through the binary denylist

**MEASURED.** `ban.assert_not_banned` inspects `Path(argv[0]).name` only:

```
  PASSES: ['env', 'python3', '/tmp/x.py']
  PASSES: ['env', 'DESKTOPINTEGRATION=false', '/usr/bin/todoist']
  PASSES: ['flatpak', 'run', 'org.x.App']
  PASSES: ['/usr/bin/distrobox-enter', '-n', 'box', '--', 'bash']
  PASSES: ['python3', '/tmp/x.py']
  blocked: ['rm', '-rf', '/home/x']     (Banned binary: rm)
  blocked: ['pkexec', 'gparted']        (Banned binary: pkexec)
```

`env`, `flatpak` and `distrobox-enter` all execute an arbitrary following
command, and none is examined. `python3` is not banned at all.

> **2026-09-03 (ADR-117, M2 and M3).** Still open — `assert_not_banned` still
> inspects only `argv[0]`. Two things underneath it were repaired, both of them
> preconditions for fixing this safely in Phase 3. **M2:** nothing asserted the
> executor *calls* the ban list at all — `assert_not_banned(argv)` could be
> replaced with `pass` and 42 security tests stayed green, the adversarial and
> injection suites included; `tests/test_executor.py::test_banned_argv_is_denied_at_dispatch`
> now fails when it is. **M3:** the `rm` entry in `BANNED_BINARIES` was the one
> entry its own test could not protect, because `["rm","-rf","/"]` is caught by
> the `"rm -"` substring rule too; the test now also feeds
> `["rm","/home/bittusah/notes.db"]` and `["dd","of=/dev/nvme0n1"]`, which only
> the binary rule rejects. Widening this gate to resolve wrapper prefixes is
> still the Phase 3 job.

**And this is reachable from real files.** `~/.local/share/applications` is
`drwxr-xr-x`, user-writable, holding 13 entries today. One of them already
uses a wrapper:

```
  todoist  ('env', 'DESKTOPINTEGRATION=false', '/usr/bin/todoist', '--no-sandbox')
```

So the argv Friday executes is **partly determined by files this project does
not write**. That is a real change to invariant #2 ("code builds argv") and no
comment anywhere flags it.

Also measured: `debian_box → ('foot','-e','/usr/bin/distrobox','enter','debian-box')`
— a voice-reachable container shell, a different privilege domain from the
curated `terminal`.

**Fix:** resolve the *effective* binary through wrapper prefixes before the
denylist check, and treat "argv originated outside our control" as its own risk
tier.

### F22 — S2 — Invariant #7 on the session-summary path is enforced by a prompt

**NEW in v2. READ.** `store/summarizer.py:distill_dialogue` sends the **raw

### F23 — S2 — The eval gate's stated 90% threshold is not enforced, and a new failing fixture cannot regress

**NEW in v2. READ.**

### F12 — S3 — The dispatch chain is the scaling ceiling

19 `if plan.name == …` branches in one 858-line module (`turn.py:263-366`).

A new capability requires edits in **seven** places:

1. `llm/schema.py` — `PARAM_SCHEMA`
2. `llm/prompt.py` — a `SYSTEM_POLICY` line (**+tokens on every turn**)
3. `llm/prompt.py` — a `CHAT_SYSTEM` clause
4. `tools/registry.py` — a `ToolSpec` (if it is a subprocess)
5. `turn.py` — a branch **and** its confirm policy, hand-written
6. `tests/fixtures/eval.jsonl` — a fixture
7. `tests/test_prompt.py` — a keyword in the coverage map

Every recent defect is a step someone skipped: F2 is #3, F3 is #6, D26 was
`STT_HOTWORDS` (an eighth site), F21 is `describe_action` (a ninth). The problem
is not discipline; it is that there are nine places.

**`ToolSpec.risk` already exists and drives nothing.** Its only use is
`tests/test_registry.py:12`. The confirm policy it was obviously meant to
express is hand-coded in `turn.py` instead — `clipboard_set`, `clipboard_read`,
`system_wifi{off}`, `hypr_window{close}`, settings-panel apps.

**Token cost:** `SYSTEM_POLICY` is **1298 tokens, measured**, one line per
action. Prompt processing is cached, so the cost is not mainly latency — it is
that the model's attention over a growing menu degrades, and the menu is the
only thing telling it what exists.

### F13 — S3 — Whole-utterance TTS is the largest latency term

`tts.py:192` — `say()` calls `kokoro.create(text)` on the **entire** string,
then opens the output stream. `on_play()`, the TTFA mark, fires after synthesis
completes.

**Measured:** 354 ms for 10 characters, **2495 ms for 117**. RTF 0.27–0.40.
Time-to-first-audio is proportional to reply length. Splitting at the first
sentence boundary makes the first chunk ~350 ms regardless of total length.

Highest felt-speed per unit of work in the system, and it is one method.

### F14 — S3 — One action per turn

`Plan` holds exactly one `name` + `params`. "Open my browser and play some
lo-fi" can only be one of the two.

**MEASURED — a multi-action grammar works on this stack today:**

```
 "open my browser and turn the volume up"
   -> 2 actions, 1511 ms
 "open my browser, play some lo-fi, and turn the volume down"
   -> 3 actions, 1662 ms
      {"actions":[{"name":"open_app","params":{"app":"browser"}},
                  {"name":"youtube_search","params":{"query":"lo-fi music"}},
                  {"name":"system_volume","params":{"direction":"down"}}]}
```

GBNF bounded repetition `{0,2}` is supported by this llama.cpp build; an
explicit-alternation form works identically.

**The cost is real and was not in v1 of my design:** the multi-action grammar
adds **+109 ms to every single-action turn** (816 → 925 ms p50), and a
three-action plan costs **1.5–1.7 s of planning alone**. See design §8.

### F15 — S3 — There is no filesystem surface

### F16 — S3 — Two independent microphone streams

`Recorder` (`capture.py:101`) and `WakeListener` (`wake.py:358`) each open their
own `sd.InputStream` on the same device.

- The audio STT transcribes is **never AEC-processed**; only the wake/VAD stream
  is. VAD decides "speech ended" using frames STT never sees.
- A dropped block on one stream shifts it relative to the other, undetectably.
- Device open/close races on suspend/resume are doubled.

Prerequisite for any serious echo-cancellation work: today the canceller and the
consumer are not looking at the same audio.

### F24 — S3 — SearXNG is a Docker dependency on a root daemon, and nothing says so

**NEW in v2. READ.** `deploy/searxng/friday-searxng.service` runs
`docker run --rm --name friday-searxng -p 127.0.0.1:8888:8080 …`.

Consequences that belong in the trust base and in the bootstrap:

- Friday's search capability depends on **dockerd, running as root**. The unit
  even documents that it cannot express the dependency, because a `--user` unit
  cannot depend on a system service.
- The container binds `0.0.0.0:8080` internally; only the host-side publish
  (`127.0.0.1:8888`) keeps it off the network. That is correct — but invariant
  #8 is being upheld by a docker port-map argument, not by the service config,
  and `settings.yml:7` literally reads `bind_address: "0.0.0.0"`.
- The image **is** digest-pinned (`sha256:11a9b34c…`). Good, and rare.
- `settings.yml:9` commits `secret_key: "friday-local-only-not-a-network-secret"`
  to git. Harmless on loopback, but it is a credential-shaped string in a
  tracked file.

None of this is wrong. It is undocumented, and a bootstrap that does not handle
Docker will fail on a fresh machine.

## H. Decisions

All eight questions from v1 were answered on 2026-09-02. The answers and the
resulting design are in **`design-2026-09-02.md` §0**.

Summary: hard cap at **(b)** (typed capabilities + owner-authored recipes); file
operations gated by **PTT + spoken confirm** now, voiceprint deferred until
provable; apps confirm **on first use, then remembered**; **multi-action turns
yes**; recipes **owner-authored, no arguments**; vision an **opt-in skill**;
**bootstrap required**.

**One answered decision has been reopened by this re-check.** The latency target
of 1.5 s / 2.5 s was chosen from a budget that assumed streaming STT. F26 shows
that is not possible on this backend. The floor is **~2.0 s** unless invariant
#6 is amended to let STT use CUDA. That question is live and is stated in the
design file.
